PROJECT OVERVIEW
================================================================================
Xencryptio is a microservices-based security scanning platform that performs 
comprehensive Post-Quantum Cryptography (PQC) readiness assessments including:
- TLS/SSL scanning for websites
- Repository scanning for cryptographic algorithms
- System/Agent scanning for installed cryptography
- Unified PQC scoring across all scan types
- Multi-organization onboarding and management

Architecture: Docker-based microservices with PostgreSQL database
Frontend: React + TypeScript + Vite
Backend: Python FastAPI services

                     2. CRYPTO/TLS SCANNER API (PORT 8000)
================================================================================
Base URL: http://localhost:8000
Purpose: SSL/TLS domain scanning using SSL Labs API

--------------------------------------------------------------------------------
CORE SCANNING ENDPOINTS
--------------------------------------------------------------------------------
POST /scan
     Body: {domain: "example.com,example2.com", max_concurrent: 5, save_to_db: true}
     → Scan domains with retry logic, filters out HTTP domains
     Returns: {summary, successful_scans, failed_scans}

POST /scan-with-progress
     Body: {domain: "example.com", max_concurrent: 5, save_to_db: true}
     → Scan with Server-Sent Events (SSE) for real-time progress
     Returns: SSE stream with events:
       - start: Initial scan info
       - domain_processing: Domain scan started
       - domain_complete: Domain scan finished
       - round_start: New retry round started
       - complete: All scans finished
       - cancelled: Scan cancelled

POST /create-scan-request
     Body: {domain: "example.com", max_concurrent: 5, save_to_db: true}
     → Queue scan request (database-centric architecture)
     Returns: {batch_id, status: "pending"}

POST /process-pending-scans
     → Process queued scans (called periodically)
     Picks up scans with status=pending and executes them

GET  /cancel-scan/{request_id}
     → Cancel ongoing scan

--------------------------------------------------------------------------------
RESULT RETRIEVAL ENDPOINTS
--------------------------------------------------------------------------------
GET  /batch/{batch_id}
     → Check batch status and statistics
     Returns: {batch_id, status, successful_count, failed_count, execution_time_seconds}

GET  /results/batch/{batch_id}
     → Get all results for a batch
     Returns: {results: List[ScanResult]}

GET  /batches?limit=100
     → Get all batches

DELETE /batches/{batch_id}
     → Delete specific batch

DELETE /batches/clear-all
     → Clear all scan data

GET  /health
     → Health check

--------------------------------------------------------------------------------
CACHE & UTILITY
--------------------------------------------------------------------------------
POST /clear-cache
     → Clear SSL Labs cache

GET  /
     → API documentation

                    3. REPOSITORY SCANNER API (PORT 8003)
================================================================================
Base URL: http://localhost:8003
Purpose: Scan GitHub repositories for cryptographic algorithms

--------------------------------------------------------------------------------
SCAN MANAGEMENT
--------------------------------------------------------------------------------
POST /api/scan
     Body: {repo_url: "https://github.com/user/repo", branch_name: "main"}
     → Queue repository scan
     Returns: {scan_id, status: "pending"}

POST /api/scans/{scan_id}/execute
     → Execute pending scan (background processing)
     Updates scan status to "in_progress" then "completed"

GET  /api/scans?limit=200
     → Get all scans (paginated)
     Returns: List of scan summaries

GET  /api/scans/{scan_id}
     → Get detailed scan results including:
       - algorithms: Dict of found algorithms with scoring
       - quantum_readiness_percentage
       - category_scores: Scores by algorithm type
     Returns: Complete scan details

DELETE /api/scans/{scan_id}
     → Delete scan and all results

DELETE /api/scans
     → Delete all scans

--------------------------------------------------------------------------------
ALGORITHM & FINDING DETAILS
--------------------------------------------------------------------------------
GET  /api/scans/{scan_id}/algorithm/{algorithm_name}/findings
     → Get all code findings for specific algorithm
     Returns: List[{file_path, line_number, context, match_text}]

--------------------------------------------------------------------------------
VALIDATION & UTILITIES
--------------------------------------------------------------------------------
POST /api/validate-url
     Body: {repo_url}
     → Validate repository URL format
     Returns: {valid: bool, normalized_url, platform}

POST /api/fetch-branches
     Body: {repo_url}
     → Fetch available branches for repository
     Returns: {branches: List[str], default_branch}

GET  /api/pending-scans
     → Get list of pending scans in queue

Base URL: http://localhost:9500
Purpose: Centralized PQC scoring for all scan types

--------------------------------------------------------------------------------
SCORING ENDPOINTS
--------------------------------------------------------------------------------
POST /api/v1/score/tls-scan
     Body: {
       scoring_type: "tls",
       algorithms: [{name, algorithm_type, key_size, position, context}],
       metadata: {source, domain, protocols},

     Body: {
       scoring_type: "repository",

     Body: {
       scoring_type: "agent",

     }
     → Score agent audit results
     Returns: Scored algorithms with security levels

POST /api/v1/score/generic
     Body: {
       scoring_type: "generic",
       algorithms: [{name, algorithm_type}]
     }
     → Generic algorithm scoring

POST /api/v1/score/algorithms

================================================================================
                        SCORING ALGORITHM DETAILS
================================================================================

Universal Scoring Service Logic:
--------------------------------

1. ALGORITHM CLASSIFICATION:
   Each algorithm is classified by:
   - algorithm_type: kex, signature, symmetric, hash
   - quantum_resistance_type:
     * fully_resistant: PQC algorithms (Kyber, Dilithium, etc.)
     * grover_resistant: Symmetric with sufficient key size
     * vulnerable: RSA, ECDSA, traditional DH
     * deprecated: DES, RC4, MD5, SHA1

2. SCORING FACTORS:
   - Base Score: Intrinsic algorithm security (0-100)
   - Key Size Multiplier: Adjusts score based on key length
   - Position Weight: Higher priority algorithms scored higher (TLS)
   - Occurrence Weight: Frequency of use (Repository scans)
   - Deprecation Penalty: Heavily penalizes weak algorithms

3. GRADE CALCULATION:
   A+: 95-100 (Fully PQC ready)
   A:  85-94  (Strong quantum resistance)
   B:  70-84  (Moderate resistance with large keys)
   C:  50-69  (Some quantum vulnerability)
   D:  30-49  (Significant vulnerability)
   F:  0-29   (Critically vulnerable)

4. QUANTUM READINESS:
   - quantum_ready: All critical algorithms are quantum-resistant
   - hybrid_ready: Mix of quantum-safe and transitional algorithms
   - vulnerable: Relies on quantum-vulnerable algorithms

5. COMPONENT SCORES:
   TLS Scans:
   - KEX (Key Exchange): Weight 40%
   - Signature: Weight 30%
   - Symmetric: Weight 20%
   - Hash: Weight 10%

   Repository Scans:
   - Weighted by occurrences
   - Category-specific grading
   - Overall readiness percentage

   Agent Scans:
   - OpenSSL configuration
   - Installed certificates
   - TLS/SSL settings
   - SSH configuration


================================================================================
                        ERROR HANDLING PATTERNS
================================================================================

All services use consistent error response format:
{
  "detail": {
    "error": "error_code",
    "message": "Human-readable message",
    "timestamp": "ISO 8601 timestamp"
  }
}

Common Error Codes:
  - validation_error: Request validation failed (422)
  - not_found: Resource not found (404)
  - internal_error: Server error (500)
  - batch_not_found: Scan batch not found (404)
  - rate_limited: SSL Labs rate limit (429)
  - dns_resolution_failed: Domain unreachable (503)

Retry Strategies:
  - TLS Scanner: 3 rounds with exponential backoff
  - Repository Scanner: Queue-based, automatic retry
  - Agent Scanner: Configurable timeout, manual retry

================================================================================
                         KNOWN ISSUES & LIMITATIONS
================================================================================

1. SSL Labs Rate Limiting:
   - Max 25 domains per 24 hours from single IP
   - Use cache where possible
   - Implement exponential backoff

2. Repository Cloning:
   - Large repositories take significant time
   - Memory intensive for file scanning
   - Consider timeout adjustments

3. Agent Communication:
   - No automatic agent discovery
   - Manual deployment required
   - Firewall rules must allow agent-to-server communication

4. Frontend Polling:
   - 1-second polling may be excessive for large batches
   - Consider WebSocket upgrade for production

5. Data Normalization:
   - Domain matching requires careful normalization
   - www. prefix handling
   - Protocol stripping consistency
